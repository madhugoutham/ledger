# Build the leaderboard on pingboard's bones, GraphQL's budget

A pingboard-style static page can deliver the full feature set (per-user PRs and reviews per repo, roll-ups per org, and an org-wide leaderboard across llm-d, vllm-project and opendatahub-io) with nothing but a browser-held GitHub token, and the build should copy exactly four things from `mgoin/pingboard`: its 20-line `gql()` wrapper that captures `x-ratelimit-*` headers, its sessionStorage-by-default/localStorage-on-opt-in token store, its 150-point rate floor, and its no-build vanilla HTML/JS/CSS layout. Nothing else surveyed is in the same architectural class; every other open-source leaderboard (OSS Insight, DevStats, GrimoireLab, github/contributors, chatwoot-contributors, coderats) needs a cron job, a server or a GH Archive database ([research note](https://github.com/mgoin/pingboard)). On the data side, two GraphQL primitives do all the work: `user.contributionsCollection(organizationID:, from:, to:)` gives a per-user, per-org, per-repo breakdown of commits, PRs, reviews and issues for **1 point per call** (three orgs aliased in one request), and `search(type: ISSUE, query: "is:pr is:merged org:X merged:A..B")` grouped client-side by author builds the leaderboard for **1 point per 100 PRs**; a full top-50 refresh of all three orgs costs roughly **150 to 250 points** against a 5,000-point hourly budget ([GitHub GraphQL rate limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)). For design, the evidence points to `Dammyjay93/interface-design` (the only mainstream skill scoped to dashboards) plus `educlopez/ui-craft`'s `dashboard.md` rulebook as explicit prompt text, with `anti-slop` or `/interface-design:design-deslop` as a second-pass review, and a GitHub-dark palette (`#0d1117` canvas, `#30363d` hairlines) that two skills independently converge on. The research literature adds non-negotiable constraints the build must honour: rank on at least three dimensions (merged PRs, reviews, issues) rather than one count, default to a 90-day window instead of all-time, show a short top-N, exclude bots, publish the method, and state on the page that the board is not a performance tool. The sections below give the concrete choices, the paste-ready queries, and the places where the research hit walls.

## Only pingboard is a true zero-backend static app; borrow its plumbing, not its code

The survey of fifteen-plus contributor-leaderboard projects split cleanly into three architectures, and only one matches the brief. The big analytics platforms ingest GH Archive into a database: OSS Insight (about **2,500 stars, Apache-2.0**) loads more than 8 billion GitHub events into TiDB and renders ECharts via Docusaurus ([SourcePulse](https://www.sourcepulse.org/projects/584142), [OSS Insight blog](https://ossinsight.io/blog/why-we-choose-tidb-to-support-ossinsight)); CNCF DevStats (130 stars, Apache-2.0, Go + PostgreSQL + Grafana) adds company affiliation via `cncf/gitdm` ([GitHub](https://www.github.com/cncf/devstats)); GrimoireLab is GPL-3.0 and therefore off-limits for code reuse ([gittrend.io](https://gittrend.io/repo/chaoss/grimoirelab)); and CHAOSS Augur was archived on 23 July 2026 with a pointer to its fork CollectOSS ([GitHub](https://www.github.com/chaoss/augur)). A second tier runs a GitHub Action on a schedule and commits JSON back to the repo for a static page: the official `github/contributors` Action (158 stars, MIT, Python) uses the REST list-contributors endpoint and flags new-versus-returning contributors with per-repo commit columns ([GitHub](https://github.com/github/contributors), [GitHub Blog](https://github.blog/open-source/maintainers/how-to-gain-insight-into-your-project-contributors/)), and `chatwoot/chatwoot-contributors` refreshes every six hours to gh-pages ([GitHub](https://github.com/chatwoot/chatwoot-contributors)). A third tier keeps a live server plus cache (coderats on Next.js + Firestore, Opensource-Contribution-Leaderboard on pm2, github-readme-stats as a Vercel function with a 24-hour cache).

The one exception is **`mgoin/pingboard`** (1 star, 9 commits), a vLLM PR-shepherding board that is "no server, no build step, no dependencies": `index.html`, `app.js`, `styles.css`, served by `python3 -m http.server` or GitHub Pages, calling `api.github.com` directly from the browser with the viewer's PAT ([GitHub](https://github.com/mgoin/pingboard)). Its 2,474-line `app.js` was read in full and the reusable parts are precise. Tokens load as `localStorage.getItem(TOKEN_KEY) || sessionStorage.getItem(SESSION_KEY)`, with `connect()` validating via `GET /user` and storing in localStorage only when "Keep token after closing this tab" is ticked; a `storage` event listener syncs tabs; `signOut()` on HTTP 401. The `gql()` wrapper POSTs `{query, variables}` to `/graphql` with `Authorization: Bearer`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, then reads `x-ratelimit-remaining/limit/reset` into state. A `tick()` scheduler treats `remaining < RATE_FLOOR (150) && now < reset` as throttled, multiplies TTLs by 5 when `document.hidden`, runs `REFRESH_CONCURRENCY = 4`, and caches search results for 60 seconds keyed by the full query string ([pingboard app.js](https://raw.githubusercontent.com/mgoin/pingboard/main/app.js)). The UI copy "The token stays in this browser and is sent only to api.github.com" is the right disclosure to reuse verbatim.

One caveat governs how much to lift: pingboard's license was not visible on its repo page and remains unverified, as does chatwoot-contributors'. Until a LICENSE file is confirmed, re-implement the patterns rather than paste the code. Everything else worth borrowing is permissively licensed (github-readme-stats MIT, github/contributors MIT, coderats MIT, OSS Insight Apache-2.0, DevStats Apache-2.0).

## Two GraphQL primitives cover every view for under 250 points

The per-user view should be driven by `contributionsCollection`, not by search. Its arguments are `from`, `to` (defaulting to one year back and clamped to a one-year span) and `organizationID`, and it returns `totalCommitContributions`, `totalPullRequestContributions`, `totalPullRequestReviewContributions`, `totalIssueContributions`, plus `commitContributionsByRepository`, `pullRequestContributionsByRepository`, `pullRequestReviewContributionsByRepository` and `issueContributionsByRepository`, each with a `maxRepositories` argument that defaults to 25 and should be raised to 100 ([GraphQL Users reference](https://docs.github.com/en/enterprise-server@3.17/graphql/reference/users)). That one call, with the three org node IDs aliased, yields the "PRs and contributions in each repo, consolidated per org" the brief asks for. Org node IDs come from a single `organization(login:) { id }` query cached in localStorage ([GraphQL Orgs reference](https://docs.github.com/en/enterprise-server@3.21/graphql/reference/orgs)). For "all time," iterate yearly windows and sum. The accounting rules behind these numbers matter for how they are labelled: commits count only when the author email is linked to the account, the repo is a non-fork, and the commit is on the default branch; co-authored commits must meet the same criteria; and PRs or issues opened in forks never count ([GitHub contribution rules](https://docs.github.com/en/enterprise-server@3.9/account-and-profile/setting-up-and-managing-your-github-profile/managing-contribution-settings-on-your-profile/why-are-my-contributions-not-showing-up-on-my-profile)).

Drill-down lists of individual PRs use `search`. The qualifier string is identical to the GitHub search box: `author:USER` matches PR creators, `reviewed-by:USER` matches any review state (add `-author:USER` to exclude self-reviews), `review-involves:` persists after review whereas `review-requested:` disappears, `involves:` is the OR of author/assignee/mentions/commenter and over-counts, and `org:ORGNAME` scopes to an organization ([Searching issues and pull requests](https://docs.github.com/en/search-github/searching-on-github/searching-issues-and-pull-requests)). Search returns `issueCount` as the total and **caps retrievable results at 1,000**, paging 100 at a time ([GraphQL search reference](https://docs.github.com/ja/enterprise-server@3.17/graphql/reference/search)). A `first: 1` query still returns the full `issueCount`, so summary tiles (open / merged / closed-unmerged / reviewed / issues) can be filled with tiny queries before any pagination. Two semantics traps: in legacy `type: ISSUE` a space between two `org:` qualifiers means OR, while in `type: ISSUE_ADVANCED` it means AND and you must write `(org:llm-d OR org:vllm-project OR org:opendatahub-io)` explicitly ([GitHub changelog](https://github.blog/changelog/2025-03-06-github-issues-projects-api-support-for-issues-advanced-search-and-more/)); and date qualifiers without a time are UTC, so compute window boundaries with `toISOString()`.

The leaderboard is where cost discipline decides success. The recommended pipeline is Strategy A then C: search `is:pr is:merged org:X merged:A..B -author:app/dependabot -author:app/github-actions` with a flat node set (`number mergedAt additions deletions author { login __typename } repository { nameWithOwner }`), group by `author.login`, drop `__typename == "Bot"`, take the top 50, then call `contributionsCollection` for those 50 to add reviews, issues and commits. GitHub's formula charges one point per 100 requested nodes across all connections with a minimum of 1, so a flat 100-PR page is **1 point**, whereas nesting `reviews(first: 50)` inside it becomes 1 + 5,000/100 = **51 points per page**, which for a vLLM-sized window balloons to 500 to 1,500 points ([GraphQL rate limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)). Keep nested connections out of leaderboard queries entirely and get review counts from `contributionsCollection` instead. vllm-project merges far more than 1,000 PRs in 90 days, so the build must split the window (two-week slices) until each slice's `issueCount` is under 1,000; llm-d and opendatahub-io are expected to fit in one window but must be checked against `issueCount` rather than assumed. Secondary limits to respect: 100 concurrent requests, 2,000 GraphQL points per minute, and queries over 10 seconds are killed yet still charged. Append `rateLimit { cost remaining resetAt }` to every query during development to see true costs.

| Strategy | Windowable | What it yields | Cost | Verdict |
|---|---|---|---|---|
| A. `search` merged PRs by org, group by author | Yes | PR authorship, lines changed | 1 pt / 100 PRs | Use for leaderboard candidates |
| B. A plus nested `reviews(first: 50)` | Yes | Reviewer counts | ~51 pts / 100 PRs | Avoid |
| C. `contributionsCollection` per named user | Yes (≤1 yr) | Commits, PRs, reviews, issues by repo | 1 pt / user, 3 orgs aliased | Use for per-user view and top-N enrichment |
| D. `membersWithRole` → C | No | Org members only | 1 pt / 100 + 1 / member | Misses community contributors |
| E. REST `stats/contributors` per repo | No (weekly buckets) | All-time additions/deletions | 1 req / repo, 202 warm-up | Optional all-time lines view |

Token and CORS choices are simple. For public orgs a classic PAT with **zero scopes** or a fine-grained PAT with no repos and no permissions both work, because fine-grained tokens "always include read-only access to all public repositories" and have been able to call GraphQL since April 2023 ([PAT docs](https://docs.github.com/en/enterprise-server@3.22/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens), [GitHub changelog](https://github.blog/changelog/2023-04-27-graphql-improvements-for-fine-grained-pats-and-github-apps)); request the minimum so a leaked browser token has no blast radius. The API returns `Access-Control-Allow-Origin: *` and whitelists the `Authorization` header, so GitHub Pages, `file://` and any static host work without a proxy ([Using CORS](https://docs.github.com/en/enterprise-cloud@latest/rest/using-the-rest-api/using-cors-and-jsonp-to-make-cross-origin-requests)). Attribution has one wrinkle specific to these orgs: pingboard hard-codes `mergeMethod: "squash"` for vllm-project/vllm, so a squash commit's author is the PR author and "commits" collapses to "merged PRs"; the honest headline metric is therefore merged PRs plus additions/deletions from the search nodes, with commit counts shown only as a secondary column. Co-authors are invisible to both `author:` search and `stats/contributors` unless their trailer email is verified, so a `Co-authored-by` scan of `mergeCommit.message` (2 points per PR) belongs only in the single-user drill-down. Repos transferred between vllm-project and llm-d carry their whole history to the new owner under `org:` search, so historical counts can shift between orgs; filter forks with `isFork: false` on `organization.repositories` and post-filter `repository.isFork` in search results.

## Pick interface-design plus ui-craft, suppress the landing-page skills

The 2026 skill ecosystem is large and noisy, and star counts for the biggest names vary two- to fifteen-fold between sources because they were captured months apart in hyper-growth: taste-skill showed **101k stars** on its GitHub page on 22 October 2026 ([GitHub](https://github.com/leonxlnx/taste-skill)), impeccable **65.8k** on Skillselion the day before ([Skillselion](https://skillselion.com/skills/pbakaus/impeccable)), interface-design **5,834** on SourcePulse ([SourcePulse](https://www.sourcepulse.org/projects/22108831)), and anti-slop was trending #6 on GitHub JavaScript on 8 October ([Trendshift](https://trendshift.io/repositories/137042)). Popularity on X skews toward landing-page skills, and the only comparative test found, a Medium author running nine skills across a landing page, a dashboard and a settings page, singled out **interface-design** as the dashboard win ("page seven looked like it belonged next to page one") and warned that stacking two style engines produces conflicting font rules ([Medium](https://medium.com/@hii_mohit/9-best-ui-skills-for-claude-code-in-2026-i-tested-them-all-58fe42809376)). No quantitative benchmark of any design skill exists; Anthropic's own evidence is captioned before/after screenshots, including an admin dashboard that went from "standard components with minimal visual hierarchy" to "a cohesive dark theme and purposeful motion" ([claude.com blog](https://claude.com/blog/improving-frontend-design-through-skills)).

The dashboard-relevant rules concentrate in three sources and should be pasted into the build prompt in the skills' own vocabulary. From `interface-design`: type ratio about 1.2 for dense UI (14px base gives caption 11, body 14, h3 18, h1 28), a 4px or 8px spacing unit with multiples only, a 60/30/10 split with one accent ("gray builds structure; color communicates status, action, or identity"), `font-variant-numeric: tabular-nums` on every dynamic number, dark-mode elevation via lightness steps of +7/+9/+12% and borders at `rgba(255,255,255,0.06–0.12)` rather than shadows, and a ban on repeating the same icon-number-label metric card ([interface-design SKILL.md](https://github.com/Dammyjay93/interface-design/blob/main/.claude/skills/interface-design/SKILL.md)). From `ui-craft`'s `dashboard.md`, the most concrete leaderboard rulebook found: tables are "the workhorse," rows 40 to 48px with 24px avatars, status as 6px dots not pills, sentence-case 500-weight headers ("Never uppercase table headers"), text left and numbers right, sticky `thead` past about 15 rows, virtualize past 200 rows, 32px SVG sparklines, filters as ghost buttons with a low-opacity accent fill when active, a date-range selector always present, "Never show 4+ identical metric cards," and "Never green arrows for positive, red for negative" ([ui-craft dashboard.md](https://github.com/educlopez/ui-craft/blob/main/skills/ui-craft/references/dashboard.md)). From the tiny `dashboard-design-skill`: ranked rows get "a slim 3 px share bar along the row's edge," tiny-base deltas show "was 1" rather than "−100%," and screenshots are checked at 3440/1440/375px ([GitHub](https://github.com/abdiraimov-otabek/dashboard-design-skill)).

Two independent skills land on the same palette, and it happens to be GitHub's own. `indi256s/dataviz-skill` prescribes a "Linear dark aesthetic" of `#0d1117` background, `#30363d` borders, muted data colors and Inter with tabular figures ([GitHub](https://github.com/indi256s/dataviz-skill)); those are GitHub's dark-theme canvas and border tokens, which makes the page feel native next to the profiles it links to. Pair that with impeccable's "Operate" mode framing (app UI should "disappear" into the task, "earned familiarity," 1px hairline borders and tonal layering instead of shadows or glass, the "10% accent rule") ([ui-skills.com](https://www.ui-skills.com/skills/pbakaus/impeccable)). Suppress the landing-page guidance from `frontend-design` and `taste-skill` (gradient meshes, grain, asymmetry, 3x type jumps) because `anti-slop` and `ibelick/ui-skills` explicitly ban gradients and glow in exactly this context ([claudemarket.ai](https://www.claudemarket.ai/skills/miqdadbadjuber/anti-slop/antislop), [ui-skills](https://docsearch.algolia.com/mcp/docs/repo/ibelick/ui-skills)). The workflow the practitioners converged on is draft, then `critique`/`polish` or `/interface-design:design-deslop` as a review pass, then Vercel `web-design-guidelines` as a final lint (it caught missing aria-labels on icon buttons and layout shift in the Medium test), with Playwright screenshots so the agent checks its own output ([Medium](https://medium.com/@hii_mohit/9-best-ui-skills-for-claude-code-in-2026-i-tested-them-all-58fe42809376)). Read every SKILL.md before installing: one guide cites Snyk research claiming 36% of tested skills contained prompt injection, a figure the notes could not independently verify ([pasqualepillitteri.it](https://pasqualepillitteri.it/en/news/576/claude-code-skills-design-uiux-guide)). Gaps remain: no skill gave rules for column sort indicators or sort-state persistence, and none addressed a contribution leaderboard specifically.

## Research says rank on three dimensions, default to 90 days, show a short top-N

The gamification literature is unambiguous about the mechanism and its cost. Leaderboards work through implicit goal-setting: participants shown a board of initials and scores set goals at or near the top and performed at levels "similar to that of difficult and impossible goal-setting" ([Landers et al. 2017](https://experts.umn.edu/en/publications/gamification-of-task-performance-with-leaderboards-a-goal-setting/)). The same mechanism punishes everyone else. On an absolute board, top-ranked students reported significantly higher intrinsic motivation than bottom-ranked (**U=11, p=.028**), while a relative neighbourhood board eliminated the difference; the authors recommend showing only the top five or alternating absolute and relative views ([Bai et al. 2021](https://opus.bibliothek.uni-augsburg.de/opus4/files/109038/109038.pdf)). In a controlled crowdsourcing study, people held at rank 1 to 2 became complacent and chased easy points while those at rank 9 to 10 pushed through round four and then quit, and "neither pattern appeared to reflect intrinsic motivation" ([Na & Han 2023](https://www.emerald.com/insight/content/doi/10.1108/intr-12-2021-0897/full/html)). Developers specifically respond to such counters: when GitHub silently removed streak counters on 19 May 2016, across **433,138 developers** the share of 14-day streaks exceeding 100 days fell from 4.4% to 2.0%, weekend contributions dropped, and single-contribution "padding" days at the end of long streaks fell from over 40% to about 36% ([Moldon et al. 2020](https://arxiv.org/abs/2006.02371)). A public org leaderboard is a stronger social signal than a private streak counter, so the build should not reward streaks or daily consistency at all.

The developer-metrics frameworks forbid single-count ranking. SPACE states that activity metrics "should never be used alone to reward or penalize" and that a sound measure uses "a handful of metrics across at least three dimensions" ([Forsgren et al., ACM Queue](https://queue.acm.org/detail.cfm?id=3454124)); Microsoft's EngThrive is "never used for individual performance assessment" and deliberately selects metrics where gaming produces useful behaviour ([LeadDev](https://leaddev.com/reporting/is-microsofts-engthrive-framework-immune-to-goodharts-law)). CHAOSS lists eleven contribution types of which "writing code" is one, and advises excluding bots at scale, stating the capture method explicitly, and offering an opt-out ([CHAOSS](https://chaoss.community/metric-types-of-contributions/)); a 2026 review of the catalogue adds that event counts "assumed human effort per event, which AI agents have broken" and that bot detection "misses agents posting through personal access tokens" ([nesbitt.io](https://nesbitt.io/2026/05/27/chaoss-metrics-in-2026.html)). A survey of 142 OSS developers found roughly half of their labour invisible in the artefacts tools count ([Meluso et al.](https://arxiv.org/abs/2401.06889)). Hacktoberfest 2020 is the cautionary precedent for count-based recognition: a PR-per-T-shirt incentive produced tens of thousands of spam PRs within days, and the fix that worked was maintainer opt-in plus counting only `hacktoberfest-accepted` work ([DeVault](https://drewdevault.com/blog/Spamtoberfest/), [developerrelations.com](https://developerrelations.com/case-studies/overcoming-hacktoberfest-spam)). Translated to this build: count merged PRs and submitted reviews, never open PRs, and make reviews a first-class column rather than a footnote.

The GitHub-specific social research sharpens the identity question. Project owners already infer competence from activity volume and recency, misjudging an experienced developer as junior from a sparse profile ([Marlow et al. 2013](https://par.nsf.gov/servlets/purl/10038300)); heavy users feel "on stage," some commit less often and move experiments to unwatched repos ([Dabbish et al. 2012](https://www.lri.fr/~mbl/ENS/CSCW/2012/papers/Dabbish2012.pdf)); and for outsiders, women's PR acceptance drops **12.0%** when gender is identifiable versus 3.8% for men across about 3 million PRs ([Terrell et al. 2017](https://peerj.com/articles/cs-111)). Public GitHub traces are already screened by recruiters and leak work habits and time zones ([Alfieri et al. 2024](https://link.springer.com/article/10.1007/s10664-024-10544-7)). The visualization rules are equally settled: length and 2D position are the reliable preattentive channels, hue is not perceived as ordered, and pies and gauges underperform sorted bars ([NN/g](https://www.nngroup.com/articles/dashboards-preattentive/)); sparklines are "word-sized" graphics with the latest value marked and a shared scale and aspect ratio across rows ([Tufte](https://www.edwardtufte.com/?p=299)); adjacent chart colors need 3:1 contrast under WCAG 1.4.11 and red/green must never carry meaning alone given roughly 1 in 12 men with CVD ([Pearson](https://www.pearson.com/accessibility-guidelines/perceivable-principle/non-text-contrast.html), [r-statistics.co](https://r-statistics.co/Accessible-Data-Visualization-in-R.html)). Existing products already embody the windowed norm: LFX Insights ranks "by the number of contribution activities performed during the selected time period" with a 365-day default and a 3-month community default, OSS Insight uses 28-day and monthly windows with an "Exclude Bots" toggle, and OpenSauced's OSCR uses 90 days ([LFX Insights](https://insights.linuxfoundation.org/project/atlantis/contributors), [ossinsight.io](https://ossinsight.io/analyze/pingcap/tidb), [OpenSauced](https://opensauced.pizza/docs/welcome/faqs)). Every opaque single-number score surveyed (OSCR's 0 to 300, github-readme-stats' percentile letter grade) drew calibration complaints, which argues for separate sortable columns over a composite ([GitHub PR #1186](https://github.com/anuraghazra/github-readme-stats/pull/1186)).

## The concrete build: one file set, two queries, twelve rules

Architecture: three files (`index.html`, `app.js`, `styles.css`), no build step, deployed by GitHub Pages, served locally with `python3 -m http.server`. Token: ask for a fine-grained PAT with no repos and no permissions (or classic with zero scopes), validate with `GET /user`, store in sessionStorage by default with a "Keep token" checkbox for localStorage, show the pingboard disclosure sentence, display `remaining / limit` and reset time in the header, and stop fetching below 150 points. Data layer: cache org node IDs and `organization.repositories(isArchived: false, isFork: false)` lists for 24 hours; cache every `(query, window)` result for at least 60 seconds in memory and persist leaderboard snapshots in localStorage keyed by `(org, window)` with a TTL of several hours, because contribution data changes slowly and the rate budget is better spent on drill-downs than polling. Concurrency 4.

Per-user view: one aliased `contributionsCollection` call across the three orgs for the selected window (90-day default, toggles for 30/90/365/all-time via yearly iteration), rendered as one panel per org with a sorted horizontal bar per repo (merged PRs, reviews, issues, commits as four muted series in one hue) and a hero number for merged PRs across all orgs. Below it, PR lists from `search` using `is:pr author:USER org:X`, split into open / merged / closed-unmerged tabs with `issueCount` tiles filled first, then `reviewed-by:USER -author:USER org:X` for reviews, paginated 100 per page with flat nodes only. Show a per-user sparkline of weekly merged PRs over the window as the personal, non-comparative goal the Landers mechanism needs.

Leaderboard: per org and consolidated, merged-PR search in two-week slices for vllm-project (single slice for the other two until `issueCount` says otherwise), grouped by author, bots dropped by `__typename` and `-author:app/...`, top 50 enriched by `contributionsCollection`. Columns: rank, avatar + handle, merged PRs (right-aligned, tabular-nums, 3px share bar along the row edge), reviews, issues, lines changed, repos touched, with a user-selectable sort and no composite score. Default display is the top 10 with "show all 50" behind a click, and a "find me" affordance that scrolls to the viewer's own row with three neighbours above and below. Add an "Exclude bots" toggle defaulting on, a "how this is computed" footer stating the queries, the squash-merge caveat, the fork and co-author exclusions, and the sentence that this page is not used for performance evaluation. Design: GitHub-dark tokens (`#0d1117`, `#30363d`, one accent under 80% saturation reserved for the hero number and active filter), Inter or IBM Plex with tabular-nums, 14px base at 1.2 ratio, 4px grid, 44px rows, sentence-case headers, 6px status dots, structural skeletons, one-action empty state ("Enter a GitHub username" or "No merged PRs in this window"), `prefers-reduced-motion` respected, 3:1 contrast between the four series colors.

## Conclusion

The brief framed this as a search for the best tool, and the answer is that no tool exists in the required class; the build is a thin, well-disciplined client over two GraphQL primitives, and its difficulty lies entirely in cost shaping (flat queries, windowed search, enrichment only for the top-N) rather than in features. That shifts where the risk sits: pingboard's architecture is proven for one repo polled every minute, but a leaderboard that can burn 51 points per page through one careless nested connection needs `rateLimit { cost }` in every query during development and a hard floor in production.

The less obvious finding is that the research literature and the design-skill community point in the same direction for different reasons. Skills ban the "rainbow metric card" and the colored delta arrow on aesthetic grounds; NN/g and WCAG ban them on perceptual grounds; SPACE and CHAOSS ban single-count ranking on behavioural grounds; and Bai, Na & Han and Moldon show what happens to real people when those rules are ignored. A top-10-by-default, 90-day, multi-column, bot-filtered, method-disclosed board is therefore not a compromise between polish and ethics but the design both constituencies independently specify. Items still unverified and worth checking before shipping: pingboard's license file, the exact wording of GraphQL's 1,000-result cap on `issueCount`, whether a sunset date exists for legacy `type: ISSUE`, and the `mitchellh/vouch#33` consent objection to listing GitHub users without asking them.
